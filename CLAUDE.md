## Project Overview

ESP32-S3 intelligent coffee scale with grind-by-weight functionality. Features predictive grinding system, LVGL touch UI, and BLE OTA updates. Automatically grinds coffee beans to precise target weights using flow prediction and pulse correction algorithms.

## Essential Commands

All development tasks use the unified cross-platform Python tool:

```bash
# Build and upload
python3 tools/grinder.py build-upload

# Data analysis (pulls grind data + system info + diagnostics over one BLE
# connection, stores a device health snapshot in the DB, launches Streamlit report)  
python3 tools/grinder.py analyze
```

**Common Commands:**
- `python3 tools/grinder.py build` - Build firmware only
- `python3 tools/grinder.py test` - Compile and run host-side C++ regression tests (also runs in CI)
- `python3 tools/grinder.py upload` - Upload latest firmware via BLE
- `python3 tools/grinder.py export` - Export grind data to database
- `python3 tools/grinder.py report` - Launch Streamlit report from existing data
- `python3 tools/grinder.py diagnostics` - Print device diagnostic report to the terminal (also captured by `analyze` into the dashboard's Health view)
- `python3 tools/grinder.py scan` - Scan for BLE devices
- `python3 tools/grinder.py info` - Get device system information
- `python3 tools/grinder.py clean` - Clean build artifacts

**BLE OTA reliability:** Delta updates diff the new firmware against the device's *current* image, so the base must match byte-for-byte. Local dev builds match `firmware_cache/build_NNN.bin` by build number; release-flashed devices never match a local cache entry (legacy CI compiled every release as build #1; `release.yml` now seeds unique numbers ≥100001 from the commit count), so the tool fetches the published release binary by the device's firmware version into `firmware_cache/release_v*.bin` and uses that as the base. On the device, the entire incoming patch is staged in PSRAM and flash is untouched until the transfer completes (`components/delta`; 16 KB-batch streaming fallback if PSRAM allocation fails) — flash erases/writes while BLE is streaming stalled the radio enough to drop the link partway through large transfers, every time. Both clients retry transient chunk-write failures, the Python tool waits out the 30–90 s apply phase (a 30 s wait used to report false failures mid-apply), and the web flasher waits for the device's own success/error status — verifying the running version after reboot when the link drops — instead of assuming success. When the link drops *mid-upload* (host BT-stack flakiness happens even at 10 cm), the web flasher reconnects silently and restarts the transfer from the first chunk, up to 3 attempts — safe because the device aborts its half on disconnect and resumes advertising, and the protocol has no resume-from-offset. Four safety nets on top: (1) a boot-loop guard (`src/system/boot_guard*`) reverts to the other OTA slot after 3 consecutive crash resets (panic/WDT only — power cycling never counts, and an empty second slot stands the guard down); (2) the firmware serves the running image's SHA-256 over BLE (`BLE_OTA_IMAGE_HASH_CHAR_UUID`, computed as `sha256(bin minus its appended 32-byte digest)`) and the Python tool refuses any delta base that doesn't match, falling back to full; (3) both clients append a zlib CRC-32 of the patch to the END command and the device verifies its flash-staged copy before applying (old client/firmware combinations degrade gracefully); (4) every OTA outcome — success or the precise failure stage — is persisted to NVS and shown in the diagnostics report under `[OTA / BOOT GUARD]`, so failed updates are diagnosable over BLE. The delta staging and CRC code is host-tested (`tools/tests/test_delta_staging.cpp` compiles the real `components/delta/delta.c` against fake-NOR stubs in `tools/tests/support/`; boot-guard decisions in `test_boot_guard.cpp`). The patch toolchain is pinned (`detools==0.53.0`/`heatshrink2==0.14.0` in both the venv and CI) and `test_patch_compat.cpp` guards the pins: it applies a patch generated at test time by the installed Python detools with the C decoder shipped in firmware — bump the pins only if that test still passes. Releases publish a `.sha256` manifest (from rc.6); the CLI verifies fetched delta bases and the web flasher verifies its OTA download against it, both skipping gracefully for older releases.

**BLE availability:** Bluetooth is on by default and stays on — there is no inactivity auto-disable, so clients can connect at any time. The BLE stack is initialized once and never deinitialized (Bluedroid rebuilds an empty GATT table on re-init while the Arduino wrapper keeps serving its stale objects), so `enable()`/`disable()` only start and stop advertising; "off" means "not advertising". The `bluetooth` NVS namespace holds `startup` (auto-enable at boot, default true); the menu's *Enabled* toggle is not persisted, so it turns the radio off only until the next reboot. Advertising is left at the wrapper's ~20–40 ms default — do not slow it down. Slowing it to 500 ms–1 s to cut radio duty was tried and made the grinder unreliable to find and connect to: at a realistic −75 dBm it is the fast rate's repetition that carries discovery and the CONNECT_IND exchange through packet loss, and load-cell noise measures identical either way, so there is nothing to buy. Note the surface is unauthenticated — no pairing/bonding and no OTA image signature check — which is accepted under the same home-appliance threat model as the plaintext WiFi credentials.

**Web App (`tools/web-server`):** One Next.js app (strict TypeScript, Biome, pnpm; scaffolded with `create-next-app@canary`) serves everything web: the device UI, the analytics dashboard, user accounts, the cloud sync API, and a firmware release proxy. The UI is built on **Tailwind v4 + shadcn** with the `base-luma` preset (Base UI primitives — not Radix — stone neutrals, amber primary, Geist/Geist Mono, lucide); `components.json` records it, and `components/ui/*` is generated code that is formatted to house style and edited freely. Dark-only for now: `.dark` sits on `<html>` and the preset's light block is kept unused so a toggle is additive. Three tokens the preset lacks are added in `globals.css` — `--success`/`--caution`/`--serious`, on hues clear of the 45–70 amber band `--primary` owns (`critical` is `--destructive`). Dark `--primary` is deliberately lifted from the preset's value, which reads brown rather than amber on the warm near-black.

**Shell and routes:** a sidebar (`components/app-sidebar.tsx`) whose header *is* the grinder — a workspace switcher carrying connection state, version, and Connect/Add/Refresh/Rename/Forget — with the account in the footer. A grinder has **one name**: the switcher's Rename and the backup's Rename both write the localStorage registry label *and* the cloud store's name, joined on the factory MAC via `ble.renameByDeviceId()` (the registry is keyed by the browser's Web Bluetooth device id, the store by the MAC). There is no device status strip; each fact lives on the page that can act on it, and "update available" is a badge on the Update nav item. Every section is a real route: **/** (adaptive home — pairing path for new visitors, device status rows for owners), **/grinder/{get-started,update,wifi,diagnostics}** (nav: Install, Update, WiFi & Backup, Diagnostics), **/analytics** (overview), **/analytics/sessions** (nav: Grinds — TanStack data table: sort, faceted filters with counts, search, column visibility, pagination; selecting rows hands them to Compare via `?sessions=`), **/analytics/beans** (nav: Beans — see Beans & Brew Logging), **/analytics/session/[sha]** (addressable by content hash, so a link to one grind survives re-pulls, cloud syncs and factory resets), **/analytics/{compare,multi,trends,health}**, plus **/account**. Analytics state lives in `components/analytics/analytics-provider.tsx`, mounted by the analytics layout, so moving between sections never re-reads IndexedDB or drops a sync in flight. The shell itself is the `app/(app)` route group's layout; **/signin** lives in `app/(auth)` and renders one centred column with a link home rather than a sidebar of grinder routes a signed-out visitor can't use (route groups don't change URLs). `/account` follows the same row-with-its-action grammar as the rest of the app — *Signing in* (password, GitHub), a separate **Passkeys** section carrying *Add a passkey* on its heading line (a collection, not a singleton method: a row reading "This Mac" is unidentifiable without a heading over it), and one row per backup with *Copy link* inline and rename/release/delete behind a `⋯` menu — and puts the once-a-year forms (change password, delete account) in dialogs instead of leaving them expanded on the page.

**Design language:** Notion's manners in this palette — flat surfaces with hairline rules rather than cards-on-cards, restrained colour (amber for the one real action per screen), hover-revealed row actions, typography carrying the hierarchy. Numbers and identifiers are Geist Mono with `tabular-nums`; labels are sans and muted. Fully responsive: the sidebar collapses to a sheet and the session table becomes one card per grind under 640px. Long device operations (OTA, BLE pull, cloud sync) keep a persistent inline `StatusRegion` — never a toast — while short acknowledgements use sonner. There are no native `alert`/`confirm`/`prompt` calls: `ConfirmDialog` and `RenameDialog` replace them.

**Copy — the product does the talking:** A sentence earns its place only if it states a consequence the user cannot see, a constraint they would get burned by, or what to do about an error. Describing how a feature works, why it was built that way, or what happens next on the happy path is cut; what remains is expressed as *state* or as a *control*, not prose. Concretely: a `PageHeader` description holds live state (`v1.4.2 · v1.5.0 available`, `128 grinds`) or nothing — never a summary of what the page is for. Preconditions belong on the control that needs them (disabled button, terse reason beside it), not in a paragraph above it — and *unknown is not absent*, so never gate on a fact this browser has not read off the grinder yet. An `EmptyState` fills its `action` slot with the button the prose would have pointed at. A `ConfirmDialog` names the blast radius in one sentence, adds what survives only where the fear is reasonable, and says "cannot be undone" only where that is literally true. A success message drops the `✓` (the `StatusRegion` icon already draws one) and renders a required follow-up as a link, not as directions to a nav item. Buttons name the outcome, not the mechanism — `Pull grinds`, not `Connect & pull data`; the BLE lease is not the user's business. Resting state and live progress are different vocabularies and must never share a formatter: state renders as `StatRow` rows, progress as short present-tense phrases ("Joining the network…"). One function serving both is what turned the WiFi panel into a commentary track. Voice is "the grinder", never "your grinder", with the subject dropped wherever context supplies it. **One name per thing** — synonyms breed glosses, which is how explanatory prose grows back: the feature is *Backup* rather than "sync" precisely because a backup needs no explaining, a recorded grind is a *grind* in the interface and a *session* only where it is a data record (routes, ids, export keys, DB tables), and the shareable URL is always a *share link*. The one exemption is analytical text on charts — what an FFT of the detrended weight signal shows, what a 50 Hz loop target means — which teaches the reader to read the data rather than excusing a product decision, and stays.

**BLE and data:** all BLE flows share one GATT connection via the `lib/client/ble.ts` singleton (chooser once, 30 s idle auto-release, clock sync + snapshot reads on every connect, silent background refresh on Chrome 117+ via `getDevices()`; known grinders persist in `grinderRegistry` localStorage keyed by device id; React consumes it through `useSyncExternalStore` in `lib/client/use-grinder.ts`). Operations that outlast the idle window — firmware upload, grind-data export, the diagnostics stream — must claim the link with the nesting `hold()`/`releaseHold()` lease (always paired in a `finally`); while any holder is active `release()` is a no-op, so a concurrent flow can't arm the idle timer and disconnect mid-transfer. The binary parser (`lib/parser.ts`) is shared by the browser dashboard AND the server's ingest validation — one TS parser; any `grind_logging.h` struct change must update it alongside the Python parser (see `tools/ble/CLAUDE.md`). Grind data chunks are delivered as acknowledged BLE indications; the firmware retries unconfirmed chunks rather than dropping them.

**Charts:** Plotly via `plotly.js-dist-min`, pure figure builders in `lib/analytics/figures.ts`, rendered flat — `paper_bgcolor` matches the page, so charts read as document content rather than embedded widgets. Series colours are *semantic* (weight/flow/target/detection), not categorical, so they stay distinct hues rather than folding into the preset's monochrome `--chart-*` ramp. The palette is validated with the dataviz skill's validator against the surface **under `--pairs all`, not adjacent pairs** — adjacent-only checking previously hid a real defect where the detection violet sat below the normal-vision floor against the weight blue. Re-run it after any series colour change. Firmware releases are listed and streamed same-origin through `/api/firmware[/tag/asset]` (GitHub releases API + asset proxy) — there is no GitHub Pages deployment and no CI asset copying; the app deploys to Vercel or self-hosts via `docker compose up`.

**Cloud Sync (docs/CLOUD_SYNC.md):** Grind sessions upload to a cloud store — hosted (Vercel) or self-hosted (`tools/web-server`, `docker compose up`: Next.js app + Postgres via Drizzle). The device holds `{server_url, store_id, upload_key, view_key}` in the `cloudsync` NVS namespace, provisioned over BLE from the web app's **WiFi & Backup** panel (`BLE_SYSINFO_CLOUD_CONFIG_CHAR_UUID`, write-only, same deferred-write pattern as WiFi; JSON readback on `BLE_SYSINFO_CLOUD_STATUS_CHAR_UUID` deliberately hands out `store_id`+`view_key` — read-only claim-by-possession — but never the upload key). Off until provisioned. `CloudSync` (`src/system/cloud_sync.*`) is the second `WifiService` consumer: after SNTP the still-open window enters an `UPLOADING` state that runs one blocking HTTP op per loop pass (grind/OTA/export gating re-checked between ops) — manifest handshake (one `(session_id, timestamp, size, checksum)` tuple per file on flash; server replies with what it lacks), one verbatim-bytes POST per wanted session, then a compact health snapshot. Zero sync state on the device; a wiped server just asks for everything again. New sessions bring a window forward after a 15 s settle. HTTPS validates via the ESP-IDF CA bundle; plain http works for LAN self-hosts. Session headers now carry a real zlib CRC-32 (legacy files have 0; the server verifies when nonzero). Server-side: raw blob is truth (Postgres `bytea`), an 80-byte summary parsed at ingest is the query index, dedup on `(store_id, sha256)` — so a factory-reset device's reborn session ids coexist and re-uploads are dropped silently. **Stores belong to user accounts** (Better Auth in `tools/web-server/lib/auth-server.ts`: email/password always, passkeys on top, GitHub button when `GITHUB_CLIENT_ID/SECRET` are set; `BETTER_AUTH_SECRET` required in production, no password reset by design — no mail service). Browser store management (create/rename/delete/provision/rotate) is owner-session-only; `authStore` tries the owner's cookie before bearer keys, so the device's key-authed ingest is untouched. Two keys, one job each: `upload_key` is the device credential, stored hashed and **rotated on every provision** (`POST /api/stores/[id]/provision` — any signed-in owner browser can provision; a DB dump leaks no write credential); `view_key` is the semi-public read credential (stored plaintext) behind share links and BLE claims. **One grinder, one store:** `stores.device_id` (the ESP's factory MAC, already sent as `x-device-id` on every request) under a partial unique index makes the 1:1 rule a DB constraint, not UI etiquette. `POST /api/stores` requires a device id and is idempotent per grinder — your own grinder returns its existing store with a rotated upload key, so a second browser, a Forget Sync or a factory reset lands back on the same history instead of orphaning it; the WiFi & Backup panel therefore reads the grinder live over BLE rather than trusting the cached snapshot, and that panel is the only place a store is born. Claiming a grinder registered to another account needs the `store_id`+`view_key` it hands out over BLE and yields an *empty* store — the previous owner keeps every grind in a now-unbound archive; `POST /api/stores/[id]/release` is the deliberate version. Key-authed ingest 403s a mismatched `x-device-id` (owner-cookie backfill exempt). Per-account store cap (`SYNC_STORES_PER_USER`) is now only a backstop; 10k-session quota rotates oldest (off in self-host). Analytics resolves its cloud source owned-stores-first (explicit pick, then the connected grinder's store, then newest; picker when an account owns several) then viewer link (records keyed by content hash in IndexedDB v2; BLE pulls retain raw bytes, auto-backfill into owned stores through the same idempotent ingest via the session cookie, and read-only dashboard links share via `#store=id:view_key`). **Annotations** (bean, roast date, grind setting, note, tags) hang off a session's content hash in the `annotations` table and in IndexedDB v3, local-first: they work with no account and sync to a store only when one exists, reconciled per row last-write-wins on `updated_at`. Grind-setting changes render as markers on the trend charts, which is the point of recording them. **Deleting a session writes a tombstone** (`deleted_sessions`) before removing the row — the manifest handshake is stateless, so without one the grinder re-uploads it on the next sync; both the manifest and `lib/ingest.ts` consult it, since ingest is reachable directly. Server ingest and the dashboard share `tools/web-server/lib/parser.ts` — one TS parser; the Python parser remains a separate consumer of `grind_logging.h`. Menu → Settings → Cloud Sync mirrors the WiFi page (toggle, status rows, Forget Sync) — the on-device menu still says *Cloud Sync* while the web app now says *Backup*; align the firmware when its strings are next touched rather than reverting the web naming. The server app is strict TypeScript linted by Biome; checks in `tools/web-server`: `pnpm test` (vitest + PGlite), `pnpm typecheck`, `pnpm lint`.

**Beans & Brew Logging (docs/CLOUD_SYNC.md "Beans and brew records"):** A bean is one bag of coffee (`beans` table: name, brew ratio, shot time default 30 s, roast date, notes, archived); `stores.active_bean_id` is the bag in the hopper, and the **server is the source of truth** — the dashboard's **/analytics/beans** page (working surface: the active bean carries shot count, deviation trend with grind-setting markers, and the advice line; the shelf is a quiet row list) writes the server first, then best-effort pushes `{name, ratio, brew_time_s}` over BLE (`BLE_SYSINFO_BEAN_CONFIG_CHAR_UUID`, deferred-write like WiFi; JSON readback + advice on `BLE_SYSINFO_BEAN_STATUS_CHAR_UUID`), while the cloud-sync window's `GET /config` fetch converges a grinder no browser is near. On-device the bag lives in the `bean` NVS namespace (`src/system/bean_config.*`). While a bean is configured, every **logged** grind (both modes; cancelled or logging-off grinds excluded) exits its completion screen into the **brew entry screen** (`UIState::BREW_ENTRY`, Delta layout: yield pre-set to dose × ratio *including top-up pulses*, edge-mounted 0.1 g jog buttons sharing the edit screen's click/hold grammar, colored deviation line — orange fast / blue slow / green within ±3%, full-width DONE, corner ✕ skips) which holds 15 min (`USER_BREW_ENTRY_TIMEOUT_MS`) before giving up unrecorded; auto-start-on-cup stays armed underneath and a new grind supersedes the unanswered prompt. DONE queues `{session_id, session_timestamp, output_g, brew_time_s}` on LittleFS under `/brews` (`src/system/brew_log.*` — deliberately not `/sessions`) and pulls a sync window forward; CloudSync's `BREW_UPLOAD` phase POSTs one record per step to `/brews`, dropping the file on `stored`/`deleted` and keeping it on `unknown` (session not uploaded yet), and every response — like the `CONFIG_FETCH` — carries `{bean, advice}`. Ingest stamps `annotations.bean_id` from the active bean (coalesce only, `updated_at` untouched); the brew lands on the session's annotation row (`brew_output_g`/`brew_time_s`), also editable in the dashboard's session Notes (bean picker replaces free text once beans exist). **Advice** (`lib/advice.ts` server, mirrored in `lib/analytics/brew.ts` — change one, change both): median deviation of the last 5 shots beyond ±8% → finer (ran fast) / coarser (choked), ≥3 shots, reset by a recorded grind-setting change; the grinder shows only the verdict as a dismissible ready-screen chip, so thresholds evolve without firmware releases. Off until a bean is provisioned — a grinder with no bean behaves exactly as before.

**Grind Data Capture:** Session logging defaults to ON (`logging/enabled` preference, toggle under Menu → Logs & Data); cancelled grinds are never saved. Session retention is space-based: files accumulate on the 3 MB LittleFS partition until free space drops below a 256 KB reserve (then oldest are purged; hard cap 250 files, roughly 100+ sessions in practice). The dashboard and Python tool warn when logging is off.

**Time Sync:** Two sources feed `src/system/time_sync.h`. (1) Every BLE client (web flasher, Python tool) writes the wall clock on connect via `BLE_SYSINFO_TIMESYNC_CHAR_UUID` (`[epoch_utc:u32 LE][tz_offset_min:i16 LE]`). (2) If WiFi is provisioned, `WifiService` (`src/system/wifi_service.h`, runs from `loop()`) syncs via SNTP at boot — so the clock survives power loss — and daily after, with exponential backoff on failure. The radio is duty-cycled (up only for the seconds a sync takes) and attempts never start — and are torn down — while a grind, OTA, or BLE data export is active. Sessions started after a sync carry real Unix epochs in `session_timestamp` (uptime seconds otherwise — no schema change; parsers distinguish by magnitude). The synced clock shows top-left on the ready screen (the top-right corner belongs to the WiFi/warning/BLE status icons, laid out in a right-aligned flex row so hidden icons collapse instead of leaving gaps) and in System Info. Both render through `TimeSync::format_local_clock()`, which honours the 12/24-hour preference (`clock` NVS namespace, key `use_24h`, default false = AM/PM; toggle under Menu → Settings → Display, loaded at boot by `TimeSync::init()`).

**Idle Clock Face:** After `USER_SCREEN_AUTO_DIM_TIMEOUT_MS` of no touch *and* no weight movement, the screen fills with the wall clock (`src/ui/screens/idle_screen.*`); `USER_IDLE_CLOCK_DIM_DELAY_MS` later the backlight drops to the screensaver level and the clock stays. Deliberately **not** a `UIState` — it is a full-screen LVGL object created last on `lv_scr_act()` (after the status icon row) so it *covers* the UI rather than replacing it. The state machine, auto-start-on-cup and the status icons keep running underneath, so a cup placed on a sleeping grinder wakes the face on contact *and* still trips the existing settled-delta auto-start on that same placement. The object is `CLICKABLE`, so the waking tap is consumed instead of hitting the button beneath it. `ScreenTimeoutController` owns the whole "nobody is here" decision (both stages) and force-wakes from `UIManager::switch_to_state()`, so a screen raised from BLE (OTA, data export) is never stranded behind the face. Wake-on-weight uses `weight_range_exceeds(USER_IDLE_WAKE_WEIGHT_WINDOW_MS, USER_IDLE_WAKE_WEIGHT_THRESHOLD_G)` — a short 1.5 s window is what makes a 0.5 g threshold safe, since drift cannot move the reading that far that fast. Suppressed while grinding/calibrating/auto-tuning, during confirmations and the OTA/export views, under the blocking overlay, and whenever `TimeSync::is_synced()` is false (an unsynced device has no honest time to show and just dims as before). The face pixel-shifts every minute — the panel is AMOLED and this view can sit lit for hours. Toggle: Menu → Settings → Display → *Clock Face* (`clock` NVS namespace, key `idle_face`, default true, cached by `TimeSync` because the controller reads it every UI frame). The bean-level readout planned for this face slots into the same shifted container.

**WiFi Provisioning:** Credentials arrive over BLE from the web app's WiFi & Backup panel (under My Grinder): `BLE_SYSINFO_WIFI_CONFIG_CHAR_UUID` (write-only: `[0x01][ssid]\0[pass]\0[tz_rule]\0[tz_name]\0` to set, `[0x02]` to forget) with JSON status readback on `BLE_SYSINFO_WIFI_STATUS_CHAR_UUID` (never contains the password). Stored in the `wifi` NVS namespace (`ssid`, `pass`, `enabled`, `tz_rule`, `tz_name`), plaintext by design (home-appliance threat model). The `tz_rule` is a POSIX TZ string derived in the browser (`tools/web-server/lib/client/tz-posix.ts`) from the browser's own DST knowledge; the firmware applies it via `setenv("TZ")`/`tzset()` so DST transitions happen locally with no network — it takes display precedence over the BLE clients' flat offset. Menu → Settings → WiFi has an enable toggle, status rows, and Forget Network. `WifiService` is deliberately a generic connection-window manager: phase-2 consumers (e.g. a session uploader firing on grind-complete) plug in without touching the lifecycle logic.

## Architecture

**4-Layer Architecture:**
1. **Hardware Layer** (`src/hardware/`): ESP32-S3 peripheral abstraction
2. **Control Layer** (`src/controllers/`): Business logic and algorithms  
3. **System Layer** (`src/system/`): State management
4. **UI Layer** (`src/ui/`): LVGL touchscreen interface

**Key Components:**
- **HardwareManager**: Central hardware coordinator
- **GrindController**: 9-phase state machine with predictive flow control, 10 pulse corrections with closed-loop flow feedback (each pulse's measured yield refines the flow estimate for the next, `pulse_flow_feedback.h`) and a cross-session pulse gain — a dimensionless EWMA of measured-vs-predicted pulse flow persisted in NVS (`pulse_gain`) that seeds the first pulse of every grind, since in-session feedback can only correct from the second pulse on — mechanical instability detection, and post-completion top-up pulses (both modes)
- **LoadCell (HX711)**: Multi-mode precision weight measurement (instant, smoothed, filtered), calibration flag, noise diagnostics
- **DiagnosticsController**: System health monitoring (calibration status, sustained noise, mechanical instability, signal saturation), state persistence, hysteresis, priority-based warnings. LOAD_CELL_SATURATED fires when raw ADC is pegged at a rail (0x000000/0xFFFFFF ± margin) for 10+ consecutive samples — indicates A+/A- wiring fault, and blocks weight-mode grinds in `GrindController::start_grind()` (time mode is unaffected)
- **UIManager**: 7 screens with LVGL integration; menu page surfaces quick Tools (Scale view, Calibrate, Tune Pulses, Motor Test) followed by Settings (Bluetooth, WiFi, Display, Grind Settings) and Info sections (Diagnostics, System Info, Logs & Data, Lifetime Stats), warning icon indicator, split-button layout for top-up pulses on the completion screen, plus the idle clock face layered above every screen (see Idle Clock Face)
- **StateMachine**: Central state coordination (READY → GRINDING → GRIND_COMPLETE)

**Update Intervals:** 20ms grind control, 25ms load cell (active), 50ms UI/hardware

**Grind Phases:**
- Standard phases: IDLE, INITIALIZING, SETUP, TARING, TARE_CONFIRM, PRIME, PRIME_SETTLING, PREDICTIVE, PULSE_DECISION, PULSE_EXECUTE, PULSE_SETTLING, FINAL_SETTLING, TIME_GRINDING, COMPLETED, TIMEOUT
- `TIME_ADDITIONAL_PULSE` - Dedicated phase for post-completion top-up pulses in **both** weight and time mode. Name kept for on-flash log compatibility (`phase_id` ordinals are decoded by `phase_names[]` in `src/bluetooth/manager.cpp`). The phase is held after the pulse until the scale settles, so `final_weight` captures the full yield
- `PURGE_CONFIRM` - Pauses after chute operation (in Purge mode) to allow user to discard grinds before continuing to main grind
- **Timeout**: 30-second maximum from grind start (includes taring), auto-stops and requires user acknowledgment

**Grinder Purge/Prime:**
- **Always runs** before weight-mode grinding to saturate the grinder for accurate latency detection
- **Prime mode**: Keeps coffee, continues immediately to PREDICTIVE phase
- **Purge mode** (default): Shows confirmation popup, waits for user to discard stale grinds, then continues
- **Configurable amount**: 0.1g-5.0g (default 1.0g), replaces old hardcoded `GRIND_PRIME_TARGET_WEIGHT_G`. Stop is coast-compensated (`GRIND_PRIME_COAST_COMPENSATION_MS`) so the configured amount is what actually lands
- **Purge popup**: "Keep purge grinds from now on" checkbox (checked by default) switches mode from Purge → Prime in preferences
- **Logging disabled** during PURGE_CONFIRM phase to avoid capturing data while paused
- **Preferences**: `chute_mode` (int: 0=Prime, 1=Purge, default=1), `chute_amount_g` (float: 0.1-5.0, default=1.0)

**Top-Up Pulses:** Split-button completion screen (OK + PULSE) in both weight and time mode, `TIME_ADDITIONAL_PULSE` phase, fixed 100ms duration (~0.1-0.2g). No re-tare and no purge, so a grind that landed at 17.8g can be nudged to 18.0g. Weight and arc update live while grounds land (the frozen `final_weight` in `emit_progress_update` only applies once back in `COMPLETED`); button is disabled during pulse+settle. Pulses are **not** reflected in the stored session log — the session is finalized on first entry to `COMPLETED`

- **Swipe Gestures Toggle**: Enable/disable vertical swipe gestures for mode switching (default: disabled)
- **Automation**: Start on Cup and Return on Removal toggles
- **Purging**: Radio buttons (Prime/Purge) and Amount slider (0.1g-5.0g)
- **Preferences**: `swipe.enabled` (boolean), `grind_mode` (0=Weight, 1=Time), `chute_mode` (0=Prime, 1=Purge), `chute_amount_g` (float)
- **Behavior**: Swipe gestures only work when enabled; direct mode selection always works

**Color Scheme (RGB565):**
- `COLOR_PRIMARY`: 0xFF0000 (Red) - Primary theme color
- `COLOR_ACCENT`: 0x00AAFF (Blue) - Highlights and accents
- `COLOR_SUCCESS`: 0x00AA00 (Green) - Success states
- `COLOR_WARNING`: 0xCC8800 (Orange) - Warning states
- `COLOR_BACKGROUND`: 0x000000 (Black) - Background
- `COLOR_TEXT_PRIMARY`: 0xFFFFFF (White) - Primary text

**Font Usage Hierarchy:**
- `lv_font_montserrat_24`: Standard text and button labels
- `lv_font_montserrat_32`: Button symbols (OK, CLOSE, PLUS, MINUS)
- `lv_font_montserrat_36`: Screen titles
- `lv_font_montserrat_56`: Large weight displays
